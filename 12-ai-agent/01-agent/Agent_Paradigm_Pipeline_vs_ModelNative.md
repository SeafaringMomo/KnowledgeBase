# Agent 范式：流水线 vs 模型原生

## 简介
构建智能体有两条根本不同的路线：**流水线范式（Pipeline-based）**把规划、工具调用、记忆交给外部代码编排，模型只是其中一个被动组件；**模型原生范式（Model-native）**通过强化学习把这些决策能力内化进模型参数，让模型自己成为那个循环。

> 分界线不是"有没有用工具"，而是**决策权在谁手里**——在代码里，还是在权重里。

## 老范式：流水线式

| 能力 | 做法 | 谁做决定 |
|---|---|---|
| 规划 | 手写 CoT/ToT 提示模板，或接入 PDDL 等符号规划器 | 开发者 |
| 工具调用 | 定义函数 schema + few-shot 示例，用 ReAct 循环驱动：模型输出调用意图，外部代码解析、执行、回填结果，再问下一步 | **外部循环（代码）** |
| 记忆 | RAG 检索、向量库、滑动窗口摘要，每轮现查现拼 | 外部检索系统 |
| 控制流 | if-else、DAG、LangGraph 节点连线 | 开发者写死 |

**典型代表**：LangChain / LangGraph 工作流、ReAct 提示工程、RPA 里塞一个 LLM 节点。

## 新范式：模型原生
用结果驱动的强化学习（GRPO、DAPO 等）把策略内化：

- **规划**：o1 起步验证可行性，DeepSeek-R1 证明仅用结果奖励即可训练出推理行为；
- **工具调用**：o3 把工具使用并入推理过程，Kimi K2 用大规模工具轨迹 + 多阶段 RL 强化多步决策；
- **记忆**：从外部检索转向参数化记忆与主动上下文管理。

## 老范式的三个死穴
1. **僵硬**——流程按预期路径设计，一偏离就崩，模型没有"绕路"的权力；
2. **上下文膨胀**——每一步工具返回值都塞回上下文，越长越贵越糊涂；
3. **天花板 = 编排者的想象力**——开发者没想到的路径，系统永远不会走。

## 新范式的代价
- 训练成本转移到模型侧，使用者**无法靠改 prompt 修正行为**；
- 分布外依然脆弱，**不可解释性更强**——出错时无法定位是哪一步策略错了；
- 长尾业务场景下，通用策略未必优于手工编排。

## 实践判断
**这个任务的步骤，能不能在写代码时穷举完？**
- 能 → 用流水线，可控、可审计、可回滚；
- 不能 → 交给模型原生，接受一定的不确定性换取适应性。

两种范式会长期共存，现实中多数系统是混合形态。
