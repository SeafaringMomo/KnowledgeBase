# RAG 基础链路

## 简介
RAG（Retrieval-Augmented Generation，检索增强生成）用外部知识库补足模型"不知道"和"记不准"的部分。核心思想很简单：**回答之前，先把相关原文找出来，放进提示词里**。但要在生产环境做对，每一环都有坑。

## 五段链路
```
文档 → ①解析/切块 → ②向量化 → ③索引/召回 → ④重排 → ⑤拼装生成
                                    ↑
                              用户问题向量化
```

| 环节 | 做什么 | 关键决策 |
|---|---|---|
| ① 解析与切块 | 把 PDF/Word/网页转成纯文本并分块 | 块大小（256–1024 token）、是否父子分块、是否按语义切 |
| ② 向量化 | 用 embedding 模型把块编码成向量 | 模型选择、维度、是否多语言/多模态 |
| ③ 召回 | 向量相似度检索 top-k，常与 BM25 关键词检索混合 | k 值、混合比例（RRF 融合）、元数据过滤 |
| ④ 重排 | 用 rerank 模型对候选重新打分 | 是否值得加（通常提升明显，但增加延迟） |
| ⑤ 生成 | 把 top-n 片段拼进提示词，要求带引用作答 | 上下文预算、引用格式、拒答策略 |

## 各环节的典型坑

**① 切块**
- 切得太碎：语义被切断，召回片段无法独立回答问题；
- 切得太大：噪声多，挤占上下文；
- **经验**：按结构切（标题/段落）优于按固定字数切；父子分块（子块检索、父块喂给模型）能兼顾精度与完整性。

**② 向量化**
- 通用 embedding 对专业术语（如工业设备型号）表现差 → 考虑领域微调或混合关键词检索；
- 换 embedding 模型必须**全量重建索引**，不能只换查询侧。

**③ 召回**
- 纯向量检索对"精确匹配型"问题（编号、型号、人名）很差 → 必须加 BM25 混合；
- 只看 top-k 会漏掉需要多跳推理的信息。

**④ 重排**
- 便宜的向量召回负责"广"，rerank 负责"准"；这一步通常是性价比最高的优化。

**⑤ 生成**
- 不要求引用 → 模型自由发挥 → 幻觉无法归因；
- 没有拒答策略 → 检索不到也硬答。

## 评估指标
| 层级 | 指标 | 说明 |
|---|---|---|
| 检索层 | Recall@k、MRR、命中率 | 先保证"该找到的找到了" |
| 生成层 | 忠实度（faithfulness）、答案相关性 | 保证"没瞎编" |
| 端到端 | 人工抽检、BLEU/ROUGE（有限参考） | 自动指标只能做趋势参考 |

> **排错顺序**：先看检索有没有召回正确片段（切 20 条问题人工看），再看生成。**80% 的 RAG 效果问题出在检索，不在模型。**

## 何时不该用 RAG
- 知识总量小且稳定 → 直接放进系统提示词更简单；
- 需要全局统计/归纳（"这批文档的主要矛盾是什么"）→ 朴素 RAG 无能为力，需要 GraphRAG 或预聚合；
- 要求强一致性的业务规则 → 用结构化查询/规则引擎，别指望向量检索。
