# Ontology 本体设计

## 简介
Ontology（本体）是**知识图谱的 schema**——规定这个领域里有哪些实体类型、哪些关系类型、允许什么连接。它是图增强 RAG 里**最难、也最容易被跳过**的一步：框架可以换，本体设计错了，换什么框架都救不回来。

> 一句行业共识：**Graph RAG 最难的部分不是框架，是本体设计。** 成功的落地团队往往在写任何检索代码之前，先花几周时间做本体。

## 本体要回答的三个问题
1. **有哪些实体类型？**（设备、故障、部件、工单、人员、规程……）
2. **有哪些关系类型？**（`发生故障`、`由...引起`、`属于`、`参照规程`……）
3. **粒度和约束是什么？**（"故障"是一个节点，还是"故障现象 + 故障原因"两类节点？）

## 粒度权衡

| | 粗粒度 | 细粒度 |
|---|---|---|
| 实体类型 | 少（10 类以内） | 多（几十类） |
| 优点 | 抽取稳定、维护简单 | 表达力强、可精确推理 |
| 缺点 | 抓不住关键区别，检索泛化 | 抽取易错、图谱噪声大、维护成本高 |
| 适用 | 早期探索、语料杂 | 领域成熟、术语规范 |

**经验法则**：**先粗后细**。先用 8–15 个核心类型跑通全链路，用真实问题验证缺什么，再逐步细分。一上来就设计 50 类实体，几乎必然失败。

## 设计方法：从问题倒推
不要从"这个领域有什么"出发，要从"**我要回答什么问题**"出发：

```
问题：这台机组近半年的振动异常，可能和哪些检修记录有关？
→ 需要：设备 —(有)— 测点 —(出现)— 异常事件 —(关联)— 检修记录
→ 实体：设备、测点、异常事件、检修记录
→ 关系：HAS_POINT、SHOWS_ANOMALY、ADDRESSED_BY
```

**只有能服务某个真实问题的实体和关系，才值得进本体。** 其余的等有需求再加。

## 常见错误
1. **把本体当成数据库表设计**：过度追求范式化，忽略 LLM 抽取的可行性——设计得再优雅，抽不出来就是零。
2. **关系方向混乱**：`A-引起->B` 和 `B-导致->A` 同时存在，图变成双向噪声。
3. **缺少实体消歧**：同一设备的多种叫法（"1号机"/"#1机组"/"一号汽轮机"）变成三个节点，多跳直接断链。
4. **不做版本管理**：本体改了但旧图没迁移，新旧数据混在一起无法查询。
5. **忽略时间维度**：工业场景里"某设备在 2025 年的状态"与现在不同，无时间属性的图会给出错误结论。

## 验收标准
一份可用的本体，应该满足：
- [ ] 每个实体类型都有**明确的定义边界**（什么算、什么不算）；
- [ ] 每个关系类型都有**方向与基数**（一对一/一对多）；
- [ ] 能用它回答**至少 10 个真实业务问题**（在纸上推演路径）；
- [ ] 有**实体规范化规则**（别名、缩写、编号格式）；
- [ ] 有**演进策略**（新增类型如何迁移旧数据）。
