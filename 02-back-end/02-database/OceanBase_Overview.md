# OceanBase 概述

## 简介
OceanBase（简称 OB）是蚂蚁集团自 2010 年起**完全自研**的原生分布式关系数据库（官方强调不基于任何开源产品）。定位：**金融级高可用的分布式 OLTP 库，附带 HTAP 能力**。

对国产化选型而言，它最大的卖点是**双模式高兼容**——同时提供 Oracle 模式和 MySQL 模式，是替换 Oracle 时改造量最小的国产库之一。

## 架构要点

```
客户端 → obproxy（反向代理，SQL 路由）
              ↓
        OBServer 集群（Shared-Nothing，节点对等）
              ↓
   Zone（可用区，可对应机架 / 机房 / 城市）
              ↓
   Partition（Hash / Range / List，支持二级分区）
              ↓
   Log Stream + Tablet（多副本，Paxos 同步）
```

- **Shared-Nothing**：每个节点都有自己的 SQL / 存储 / 事务引擎，不共享磁盘。
- **Paxos 多副本**：每个日志流一主多从，主副本故障自动切换。
- **多租户**：一个集群可开多个租户，每个租户从应用视角看就是一个独立实例，可选 MySQL 或 Oracle 模式；CPU / 内存 / IO 通过 Resource Unit 隔离。
- **obproxy**：专用反向代理，做路由与容灾，避免客户端感知数据分布。

## 关键特性

| 特性 | 具体指标 | 适用性判断 |
|---|---|---|
| 高可用 | "三地五中心"，RPO=0、RTO<8s | 金融级容灾，普通业务用不上 |
| 高兼容 | Oracle 常见功能 95%+（含 PL/SQL、包、触发器）；MySQL 5.7/8.0 大部分 | **换 Oracle 的核心价值** |
| 高压缩 | LSM-Tree 存储，存储成本降 70%~90% | 数据量大时省钱 |
| 水平扩展 | 单集群 1500+ 节点、3PB+、单表万亿行 | 超大规模 |
| HTAP | 同一份数据 + 列存副本 + 资源隔离 | 需要强一致实时分析时 |
| 多租户 | 一集群多租户，租户间数据不可互访 | 集团统一数据库时很有价值 |

性能参考：TPC-C 7.07 亿 tpmC；"双 11" 峰值 6100 万次交易 / 秒。

## 社区版 vs 企业版（容易踩的坑）

| 能力 | 企业版 | 社区版 |
|---|---|---|
| MySQL 模式 | ✅ | ✅ |
| **Oracle 模式** | ✅ | ❌ |
| XA 事务、LOCK TABLE | ✅ | ❌ |
| 仲裁服务 | ✅ | ❌ |
| 审计 | ✅ | ❌ |
| **行级标签安全（LBAC）、TDE 透明加密** | ✅ | ❌ |
| 高级执行计划管理（SPM） | ✅ | ❌ |

> **直接影响权限方案**：若打算靠 OB 的"行级标签安全"做多租户隔离，**社区版没有这个能力**，只能退回视图或应用层方案。详见[数据库访问控制](Database_Access_Control.md)。

## 与同类产品的对照

| 对比对象 | 差异 |
|---|---|
| **TiDB** | 同为分布式 HTAP。TiDB 兼容 MySQL 生态更彻底，OB 的 Oracle 兼容更强；TiDB 用 TiKV + TiFlash 分离存储，OB 用一份数据多副本形态 |
| **达梦 / 金仓** | 以集中式为主，部署与运维简单得多；OB 是分布式，为水平扩展和容灾付复杂度 |
| **Doris** | Doris 是纯 OLAP（列存），没有强事务；OB 以 TP 为主。做报表选 Doris，做交易选 OB |
| **MySQL** | OB 的 MySQL 模式可平滑迁移，但分布式带来的运维模型差异（租户、Zone、obproxy）需要学习成本 |

## 成本与失败模式

| 失败模式 | 说明 |
|---|---|
| **小场景过度设计** | 只为存几百条配置、几万行数据上 OB，等于用航母运快递——多副本、Paxos、obproxy 全是成本 |
| **忽略版本能力差异** | 按企业版文档设计，交付时是社区版，Oracle 模式 / 审计 / 行级标签全都没有 |
| **把 HTAP 当免费午餐** | 不开资源隔离，AP 大查询直接把 TP 拖垮 |
| **运维能力不足** | 分布式故障定位比单机难一个量级，需要专人 |
| **误判迁移成本** | "兼容 95%" 不等于 "零改造"，存储过程、隐式类型转换、执行计划差异仍需逐条验证 |

## 适用判断

| 场景 | 建议 |
|---|---|
| 核心交易系统替换 Oracle，且要求高可用 | ✅ OB 企业版（Oracle 模式） |
| 集团统一数据库平台，多业务共用一个集群 | ✅ OB 多租户 |
| 单表百亿行、PB 级数据 | ✅ OB |
| 大屏 / 报表 / BI 的历史查询 | ❌ 用 Doris 等列存 OLAP |
| 只存配置与用户表 | ❌ PostgreSQL / MySQL 足够 |
| 已有 OB 平台，新系统只做只读消费 | ⚠️ 可以接入，但理由应是"复用基础设施"，不是"需要 HTAP" |

## 实践建议

1. 采购前**书面向厂商确认版本能力清单**（尤其 Oracle 模式、审计、行级标签、TDE）。
2. 明确是否需要分布式。**能用集中式解决的，不要上分布式**——这是最重要的一条。
3. 若使用 HTAP 能力，必须规划**资源隔离**（租户 / Resource Unit 分配），否则分析会拖垮交易。
4. 迁移 Oracle 时先跑 **OMA 评估报告**，把不兼容对象列清楚再排期。
