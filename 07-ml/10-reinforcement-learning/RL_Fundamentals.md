# 强化学习基础

## 简介
强化学习（RL）解决的是**序贯决策**问题：智能体在环境中不断行动，根据延迟的奖励信号调整策略。它和监督学习最大的区别是——**没有标准答案，只有后果**。

一句话对比：监督学习问"这个输入的正确输出是什么"，强化学习问"在这个状态下做什么，长期回报最高"。

## 一、基本框架（MDP）

| 元素 | 含义 | 例子（工业场景） |
|---|---|---|
| State $s$ | 环境当前状态 | 机组负荷、温度、振动 |
| Action $a$ | 可选动作 | 开大/关小阀门、调整转速 |
| Reward $r$ | 即时反馈 | 能耗降低为正、超温为负 |
| Policy $\pi(a\lvert s)$ | 状态到动作的映射 | 要学的东西 |
| Value $V^\pi(s)$ | 从该状态出发的期望累计回报 | 评估策略好坏 |
| 折扣 $\gamma$ | 未来奖励的权重 | 0.9–0.99；越小越短视 |

**马尔可夫性**：假设"当前状态已包含决策所需的全部历史信息"。现实中往往不成立——所以要用 LSTM、帧堆叠或历史窗口来构造状态。

## 二、两条技术路线

### 值函数法（Value-based）
先学"每个状态—动作值多少钱"（Q 值），再选 Q 最大的动作。

$$
Q(s,a) \leftarrow Q(s,a) + \alpha\left[r + \gamma\max_{a'}Q(s',a') - Q(s,a)\right]
$$

**DQN 的两个关键创新**（让 Q-learning 能配深度学习）：
1. **经验回放**：把 $(s,a,r,s')$ 存进缓冲区随机采样，打破样本间的时间相关性；
2. **目标网络**：用一份延迟更新的参数算 TD 目标，避免"自己追自己"导致发散。

**局限**：只能处理离散动作；连续控制需要离散化（维度爆炸）或改用策略梯度。

### 策略梯度法（Policy-based）
直接对策略参数求梯度，让"高回报的动作"概率上升。

$$
\nabla_\theta J \approx \mathbb{E}\left[\nabla_\theta\log\pi_\theta(a\lvert s)\cdot \hat A(s,a)\right]
$$

| 算法 | 特点 |
|---|---|
| REINFORCE | 最基础，方差极大 |
| Actor-Critic | 用 Critic 估计优势函数，降低方差 |
| A3C / A2C | 多环境并行采样 |
| **PPO** | 用裁剪限制策略更新幅度，稳定、易调，工业默认选择 |

**PPO 的核心一句**：把策略更新限制在"信任域"内，避免一步迈太大把策略搞崩。

## 三、关键概念对照

| 概念 | 含义 | 影响 |
|---|---|---|
| On-policy vs Off-policy | 是否用当前策略采的数据 | Off-policy 样本效率高但难稳定（DQN）；On-policy 稳定但费样本（PPO） |
| 探索 vs 利用 | 试新动作 vs 用已知最优 | ε-greedy、熵正则、噪声注入 |
| 稀疏奖励 | 只在终局给奖励 | 需要奖励塑形、课程学习、HER |
| 信用分配 | 最终结果该归功于哪一步 | 这是 RL 最难的根本问题 |

## 四、RL 与 LLM 的交汇（当代最重要的应用）
大模型的**对齐与推理训练**本质上是 RL：

| 方法 | 奖励来源 | 用在哪 |
|---|---|---|
| RLHF | 人类偏好训练出的奖励模型 | ChatGPT 式对齐 |
| **RLVR** | 可自动验证的答案（数学、代码测试） | o1 / R1 类推理模型 |
| DPO | 直接用偏好对做监督式优化 | 免奖励模型的轻量替代 |

**这解释了一个现象**：为什么"会推理"的模型需要 RL——因为"多步推理的正确路径"无法用监督学习标注（没有标准中间步骤），只能用结果奖励去探索。

## 五、边界与代价

- **样本效率极低**：Atari 上百万帧才学会一个游戏；真实系统不可能这么试错；
- **仿真到现实的鸿沟（sim2real）**：仿真里最优的策略，到现场常常失效；
- **奖励设计是最大的坑**：奖励写错，智能体会**精准地钻空子**（reward hacking）——想让它跑得快，它学会了原地转圈刷分；
- **不稳定性**：超参敏感、随机种子影响巨大，复现困难；
- **安全约束难处理**：真实工业系统不允许"探索危险动作"，必须加硬约束或先在仿真中训练。

## 六、实践建议
1. **先问"能不能用监督学习/规则解决"**——80% 的工业问题不需要 RL；
2. 若必须用 RL，**先在仿真里做**，并保证仿真与真实的关键物理量一致；
3. 奖励函数要**稀疏而真实**，宁可加辅助任务，也不要写"看起来合理"的塑形奖励；
4. 用 PPO 做基线，除非有明确理由才换算法；
5. 上线必须带**安全兜底**：动作裁剪、规则否决、人工接管开关。
