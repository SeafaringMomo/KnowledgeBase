# LLM 基础与训练流程

## 简介
大语言模型（Large Language Model）本质上是一个**超大规模的下一 token 预测器**：给定前文，输出词表中每个 token 的概率分布。全部能力——推理、编程、翻译、对话——都是从这一个目标里"涌现"出来的。

> 理解 LLM 的第一性原则：**它不是数据库，不是搜索引擎，也不是逻辑引擎；它是一个用海量文本拟合出来的概率模型。**

## 三阶段训练流程

| 阶段 | 数据 | 目标 | 产物 |
|---|---|---|---|
| **① 预训练 Pre-training** | 万亿级 token 的通用文本/代码 | 下一 token 预测（自监督） | 基座模型（Base），知识量大但不能对话 |
| **② 监督微调 SFT** | 数万~数百万条指令-回答对 | 学会"按指令回答"的格式与风格 | Instruct 模型 |
| **③ 对齐 / 后训练** | 人类偏好数据、可验证奖励（RLVR） | 有用、无害、诚实；强化推理 | Chat / Reasoning 模型 |

**关键认知**：预训练决定**能力上限**，后训练决定**能力能否被调用**。基座模型什么都知道但不会听话；只做 SFT 的模型会听话但推理弱；加 RLVR 后才有长链条推理能力（o1、R1 路线）。

## 缩放定律（Scaling Law）

| 定律 | 结论 | 影响 |
|---|---|---|
| Kaplan et al., 2020 | 损失随参数量、数据量、算力呈幂律下降 | 确立"大力出奇迹"的可行性 |
| **Chinchilla, 2022** | 计算最优时，参数量与训练 token 数应同比扩展（约 **20 token / 参数**） | 纠正了"只堆参数"的偏差，同算力下小模型多数据更强 |

**实践中的偏离**：由于推理成本长期累积，现代模型普遍**用远超 20:1 的比例训练**（把成本从推理转移到训练）。Chinchilla 回答的是"给定训练算力如何最优"，不是"给定产品总成本如何最优"——成本函数变了，最优解就变了。

## 当前架构演进（2026 视角）

| 方向 | 做法 | 解决什么 |
|---|---|---|
| **MoE 混合专家** | 总参数极大，每 token 只激活一小部分专家 | 用固定计算量换更大知识容量；关键指标是"总参数 vs 激活参数" |
| **长上下文** | RoPE 外推、GQA/MQA、稀疏与线性注意力 | 缓解 O(n²) 与 KV cache 显存压力 |
| **推理模型** | 长思维链 + 可验证奖励的强化学习（RLVR） | 数学、代码、复杂规划等需要多步推理的任务 |
| **环境交互训练** | 在代码执行器、模拟器、API 中试错学习 | 从"读文本"转向"看结果"，提升真实任务鲁棒性 |

**必须知道的分野**：MoE 的"模型大小"有两个轴——**总参数决定容量与显存**，**激活参数决定每 token 的计算**。拿稠密模型的参数直觉去理解 MoE 会严重误判成本。

## 关键概念速查

| 概念 | 含义 | 实践影响 |
|---|---|---|
| Tokenizer | 文本 → token 的切分规则 | 中文 token 效率低于英文，直接影响成本 |
| 上下文窗口 | 单次可处理的 token 上限 | 不是越大越好，成本与"中间遗忘"问题并存 |
| Temperature / top-p | 采样随机性控制 | 抽取类任务用 0，创作类调高 |
| KV cache | 缓存历史 key/value 避免重算 | 长对话显存占用的主因 |
| 幻觉 Hallucination | 生成看似合理但错误的内容 | 无法根除，只能靠 RAG + 引用 + 验证缓解 |
| 知识截止 | 训练数据的时间边界 | 实时信息必须靠检索或工具 |

## 场景 / 优势 / 局限

**优势**
- 零样本泛化能力强，一个模型覆盖多任务；
- 自然语言接口，降低系统集成门槛；
- 缩放行为可预测，投入与产出关系相对明确。

**局限（决定它该用在哪）**
- **不可靠的事实源**：没有引用就无法验证，关键业务必须外挂知识库；
- **算术与精确操作用力弱**：该用代码/工具的地方不要交给模型算；
- **上下文 ≠ 记忆**：窗口再大也是一次性的，跨会话记忆必须外部持久化；
- **成本随长度平方增长**：长上下文方案要先算账；
- **不可解释**：出错时无法定位"哪一步想错了"，只能靠外部验证兜底。

## 与 Agent 的关系
LLM 是**策略（policy）**，Agent 是**策略 + 环境 + 循环**。模型决定"下一步做什么"，但能看什么、能碰什么、什么时候停，由外层的 Harness 与 Loop 决定。见 [Agent 范式](../../12-ai-agent/01-agent/Agent_Paradigm_Pipeline_vs_ModelNative.md) 与 [Loop Engineering](../../12-ai-agent/01-agent/Loop_Engineering.md)。

## 实践建议
1. **先判断任务类型**：知识查询 → RAG；格式转换 → 提示词；精确计算 → 代码工具；开放生成 → 模型直出；
2. **成本估算三要素**：输入 token、输出 token、调用次数。长上下文方案必须先做这笔账；
3. **评估先行**：准备 20–50 条真实问题的评测集，任何模型/提示词变更都跑一遍，否则优化全靠感觉；
4. **不要把 LLM 当数据库**：知识要可更新、可追溯，就必须放在模型之外。
