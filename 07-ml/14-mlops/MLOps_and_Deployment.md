# MLOps 与模型部署

## 简介
训练出一个模型只完成了 20% 的工作。剩下 80% 是：**怎么把它稳定地跑在生产环境里，并且在数据变化时不悄悄失效**。MLOps 就是这 80% 的工程体系。

> 一句话区分：**DevOps 管代码的可重复交付，MLOps 还要管数据与模型的可重复交付。**

## 一、模型交付的三种形态

| 形态 | 适用 | 延迟 | 复杂度 |
|---|---|---|---|
| **批处理（Offline）** | 日报、离线评分、批量打标 | 小时级 | 低 |
| **在线服务（Online）** | 实时推荐、风控、对话 | 毫秒–秒级 | 高 |
| **边缘（Edge）** | 产线质检、车载、离线现场 | 毫秒级 | 高（算力受限） |

**选型判据**：业务是否需要"用户请求时立刻出结果"。不需要，就别做在线服务——运维成本差一个数量级。

## 二、推理引擎与格式

| 工具 | 作用 | 什么时候用 |
|---|---|---|
| **ONNX** | 跨框架模型交换格式 | 需要在不同运行时之间迁移 |
| **ONNX Runtime** | 通用推理引擎 | CPU 部署、跨平台 |
| **TensorRT** | NVIDIA GPU 专用优化（算子融合、量化） | 追求极致延迟 |
| **TorchServe / Triton** | 模型服务框架（多模型、动态批处理） | 多模型统一托管 |
| **vLLM / SGLang** | LLM 专用推理（PagedAttention、连续批处理） | 大模型服务必选 |

## 三、MLOps 的四个支柱

| 支柱 | 解决的问题 | 代表工具 |
|---|---|---|
| **实验追踪** | 哪个超参组合产生了哪个结果 | MLflow、W&B |
| **数据/模型版本** | 这个模型是用哪版数据训的 | DVC、LakeFS、模型注册表 |
| **流水线编排** | 训练→评估→发布自动化 | Airflow、Kubeflow、Argo |
| **监控告警** | 上线后是否悄悄退化 | Prometheus + 自定义指标 |

**最小可用组合**：MLflow（追踪）+ Git（代码）+ 对象存储（数据/权重）+ 一个定时任务。**不必一上来就上 Kubeflow。**

## 四、部署流水线（CI/CD/CT）

```
代码提交 → 单测 → 训练 → 离线评估 → 模型注册 → 灰度发布 → 线上监控
                                    ↑__________________________|
                                         数据漂移触发重训（CT）
```

**CT（Continuous Training）是 MLOps 区别于 DevOps 的地方**：模型需要按数据变化周期性地重新训练，而不是一次发布管到底。

## 五、上线后必须监控的四类指标

| 类别 | 指标 | 异常信号 |
|---|---|---|
| **服务指标** | QPS、P99 延迟、错误率 | 延迟突增 → 上游依赖或批次变大 |
| **数据漂移** | 特征分布（PSI、KS） | PSI > 0.2 → 分布显著变化 |
| **预测漂移** | 输出分布、置信度分布 | 置信度整体下降 → 模型不再适用 |
| **业务指标** | CTR、准确率抽检、人工反馈 | 唯一真正重要的指标 |

> **最危险的失效模式是"静默失效"**：服务正常、延迟正常、没有报错，但预测已经不准了。只有数据漂移监控能提前发现。

## 六、灰度与回滚

| 策略 | 做法 | 适用 |
|---|---|---|
| 影子模式（Shadow） | 新模型并行跑，不对外输出 | 高风险场景，验证充分再切 |
| 金丝雀（Canary） | 5% 流量走新模型 | 通用 |
| A/B 测试 | 按用户分组对比业务指标 | 需要统计显著性 |
| 蓝绿 | 两套环境整体切换 | 需要快速回滚能力 |

**必须能一键回滚**。模型上线没有回滚预案，等于在裸奔。

## 七、边界与代价

- **工具链过重**：小团队上全套 Kubeflow，维护成本超过收益。**按规模选型**；
- **特征/训练/推理三处实现不一致**：最常见的生产事故来源（离线 Python 与线上 Java 算法不同）；
- **监控缺失是常态**：很多团队上线后只看服务是否活着，不看预测是否还有效；
- **成本结构变化**：GPU 推理成本可能是训练的数十倍（按调用量累计），选型时必须算总账；
- **合规审计**：金融、医疗场景需要完整的模型版本与决策留痕。

## 实践建议
1. **先做批处理版本**，验证业务价值后再做在线服务；
2. 模型服务统一用 **Triton 或 vLLM**，不要在业务代码里直接 load 模型；
3. 上线第一天就配好**数据漂移监控**，别等出事再补；
4. 每次发布必须带**回滚开关**与**版本号**；
5. 特征计算代码只保留一份，训练与推理共用。
